## 1. 设计边界

本设计只覆盖 Gate 3 已批准的 REQ-001 新游列表及 REQ-002 游戏详情。产品仅包含 `GAME_PUZZLE`、`GAME_CASUAL`，不限定国家/地区；不增加登录、搜索、筛选、收藏、分享、外部跳转、付费、同步、通知或其他功能。

本文是技术方案提案，不授权开始开发，也不批准需求变更。Gate 4 通过前，技术决策仍为待审核；Gate 5 任务拆解及后续开发门禁仍须分别执行。

## 2. 架构与模块职责

建议使用单 App target、SwiftUI 展示层、可注入的应用服务和 API 客户端，不引入独立服务端业务逻辑。模块按职责划分如下：

| 模块 | 职责 | 主要输入 / 输出 |
|---|---|---|
| `GameListFeature` | 列表与详情导航；呈现加载、内容、空结果、失败四种状态；不承载 API 细节 | ViewModel 的只读状态、用户点击事件 |
| `GameListViewModel` | 管理一次启动刷新、请求取消、状态转换及列表选择 | `GameCatalog`、日期时钟/日历 |
| `GameCatalog` | 聚合两个类别、分页、过滤、去重、排序，并按 ID 加载详情 | `GameAPIClient`、`ReleaseDateWindow` |
| `GameAPIClient` | 组装 `/api/v1/new` 与 `/api/v1/app` 请求，解码响应并映射传输错误 | API 配置、受保护凭据提供器 |
| `ReleaseDateWindow` | 以设备本地日历构造包含第 7 与第 15 日的时间范围，并生成 API UTC 查询包络 | 当前时刻、设备 `Calendar` / `TimeZone` |
| DTO / Domain Models | 将 API 响应与列表/详情展示数据分离；模型细节见 `DATA_MODEL.md` | 经过验证的字段 |

依赖方向为 View → ViewModel → Catalog → API Client。UI 不直接发请求；API 客户端不决定业务日期范围或 UI 状态。所有边界依赖应可替换，以便不联网测试日期、聚合与状态机。

**密钥安全是实施前置条件。** `/new` 是需认证接口，API Key 不得编译进 App、写入仓库、文档、测试证据或日志。纯客户端二进制中的静态密钥可被提取；因此在未决架构获用户批准并落地前，正式 App 不得携带真实密钥调用受保护 API。服务端代理是候选方案而非既定决定；选型见 `GATE4_REVIEW.md`。

## 3. SwiftUI 页面与状态

### 列表页

- 单一列表页面，不提供搜索框、筛选器、排序控件或外部链接。
- 每行只使用 API 已验证且需求允许的列表字段。建议显示标题、图标、类别和首次上架日期；其中 `icon`、`category`、`released` 均见 API 字典。不得展示商店 URL 或把行/图片设为外部跳转。
- 点击行进入对应详情；页面状态只允许：
  - `loading`：首次加载中。
  - `loaded([GameSummary])`：有结果，展示按 `released` 从新到旧排列的列表。
  - `empty`：仅显示 `No games found`。
  - `failed`：仅显示 `Unable to load games`。
- 加载失败页不同时展示旧列表、错误详情、重试按钮或其他提示；空结果页也只展示规定文案。

### 详情页

- 由列表行选择进入；以应用 `id` 请求 `/api/v1/app`。
- 显示策略仅限 API 实测详情字段，具体候选字段与未批准字段说明见 `DATA_MODEL.md`。不显示或使用 `url`，不提供外部跳转。
- 详情加载/失败的可见交互未在 Gate 3 明确；Gate 4 请确认是否沿用列表失败文案的约束，或允许定义详情专属错误状态。实现前必须明确，不擅自增加重试/错误操作。

## 4. 网络、分页、聚合与刷新生命周期

### 请求策略

- 列表使用 `GET /api/v1/new`，分别指定 `category=GAME_PUZZLE` 与 `category=GAME_CASUAL`，不请求 `GAME` 或其他类别，不设置国家/地区过滤。
- `per` 使用已验证上限 100。按 API 返回的 `total` 与已验证可用的 `page` 参数继续读取后续页，直到该类别符合查询范围的分页数据读完；每个类别最多读取 API 已知可访问的前 10,000 条。若结果达到 API 可访问上限仍无法证明已读完，必须将数据完整性问题视为加载失败，不把部分结果冒充完整列表。若响应无法可靠提供页数/总数/终止条件，属于需在实现前验证的 API 契约缺口。
- 两类别请求可并行执行；结果统一归并后按 `id` 去重，再按 UTC `released` 时间从新到旧排序。相同时间的稳定次序以 `id` 升序作为确定性技术排序，不增加 UI 排序功能。
- 两类均成功且完整后才能发布列表。任何一类任一页失败、解码失败或响应结构不满足契约，整次列表加载失败并只显示 `Unable to load games`；不得显示部分类别结果。
- 网络请求应设置合理超时，具体时长待实现任务定义并测试；不得记录密钥、认证头、完整请求 URL（若含敏感参数）或未经脱敏的响应。

### 本地日历日窗口与 UTC `released`

业务规则按用户设备本地日历日计算，不按滚动的 24 小时差计算。令设备当前本地日历日为 `D`，设备当前 `Calendar` / `TimeZone` 下：

1. `start = startOfDay(D - 15 calendar days)`。
2. `endExclusive = startOfDay(D - 6 calendar days)`。
3. 候选记录须满足 `releasedUTC >= start` 且 `releasedUTC < endExclusive`。这精确包含本地日期 `D-15` 至 `D-7` 共 9 个日历日，含第 15 天和第 7 天的全部时刻。
4. 先解析 API UTC ISO 8601 时间戳为绝对时刻，再与上述本地日历边界对应的绝对时刻比较；不截断 UTC 日期后直接与本地日期比较。窗口跨越夏令时变化时，以日历日边界为准，而非固定秒数。
5. `/new` 的 `since` / `until` 是日期参数，但实测材料未证明服务端日期边界的时区定义或可表达精确时刻。客户端应请求足以覆盖上述绝对时刻窗口的 UTC 日期包络（包络两端保守向外扩展至少一个 UTC 日），随后始终以客户端精确边界过滤；这样 API 端日期筛选只用于缩小候选范围，不替代业务判定。若 API 参数语义仍不足以保证该包络无漏项，需在开发前补做针对时区边界的 API 验证，或请用户决定处理方式。
- 当前时间、日历和时区必须从可注入的系统时钟/环境取得，测试可固定；刷新时快照一次 `now`，两个类别共享同一个窗口。

### 刷新生命周期

- 每次 App 进入完全启动流程时触发一次列表刷新。一次启动内不得由页面重复出现、视图重绘或从后台回前台额外触发刷新。
- App 从后台返回前台不自动刷新。首版不引入定时刷新、推送刷新、后台刷新或用户手动刷新入口。
- ViewModel 对同一启动刷新采用单飞策略：进行中的同次刷新不重复发起；若生命周期意外启动新一轮请求，应取消并隔离旧任务，旧任务不能覆盖新状态。
- 启动时显示 `loading`，请求全部成功后进入有内容或 `empty`；发生任一失败进入 `failed`。错误状态不自动重试。

## 5. 详情数据流

列表行的 `id` 作为详情请求唯一键。进入详情时 `GameCatalog` 调用 `GET /api/v1/app?id=<id>`，校验响应 `id` 与请求 ID 一致后映射为详情模型。详情不从列表字段推造 API 未返回的字段；列表中已有的信息可在详情展示前作为临时已知值，但不能据此替代详情 API 响应或声称字段已完整。详情 API 错误分类见第 7 节。

## 6. 并发与取消

- 建议采用 Swift 原生结构化并发表达类别请求和分页任务；具体 Swift 语言版本/并发严格模式待用户决定，不在本稿冻结。
- 同一列表加载作用域下两个类别并发请求；单一类别内分页顺序请求，避免对服务造成无证据支持的并发压力，并保留页序处理的可预测性。
- 父任务取消时取消两类别及当前分页子任务；离开详情页可取消未完成的详情读取。底层 URL 加载必须响应取消。
- 每次加载携带递增请求代号或任务身份；仅当前有效任务可提交状态。取消不是加载失败，不显示错误文案；被取消的旧任务不得清空或覆盖新任务结果。
- 合并、去重、过滤、排序为纯计算步骤，完成后一次性提交不可变结果，避免 UI 观察到半成品。

## 7. 错误映射

| 错误类别 | API / 客户端示例 | 列表可见结果 | 处理约束 |
|---|---|---|---|
| 传输失败 | 无网络、超时、连接中断 | `Unable to load games` | 不展示底层错误，不自动重试 |
| 认证 / 配置 | HTTP 401、缺少安全凭据 | `Unable to load games` | 不回退到内置密钥，不记录凭据 |
| 服务端 / HTTP | 非成功状态码、HTTP 5xx | `Unable to load games` | 保留脱敏诊断类别；不展示原始响应 |
| 解码 / 契约 | JSON 无法解码、必需字段缺失或类型错误 | `Unable to load games` | 整次类别聚合失败，不发布部分列表 |
| 分页不完整 | 页缺失、循环页、达到 10,000 条访问上限仍可能有余项 | `Unable to load games` | 不把不完整集合当完整结果 |
| 详情未找到 | `/app` HTTP 404 `not_found` | 详情可见状态待用户决策 | 不生成假详情，不打开商店链接 |
| 详情其他失败 | 传输、认证、服务端、解码失败 | 详情可见状态待用户决策 | 内部分类与列表错误一致；呈现待决 |
| 用户取消 | 任务被新任务/页面生命周期取消 | 不显示失败文案 | 丢弃过期任务输出 |

日志仅允许记录不含密钥、认证头、敏感 URL、原始响应或可识别用户信息的技术错误分类。首版是否保留本地诊断日志待实现任务确定；不增加遥测/分析 SDK。

## 8. 安全、存储与配置

- 绝不在客户端源码、资源、plist、构建设置、Git、日志或截图中放入生产 API Key。将 Key 放入 Keychain 仍不能防止分发客户端密钥被提取，不能作为保护共享服务凭据的充分方案。
- 生产调用所需凭据所有权、代理/API 网关、额度控制及运行环境尚未获批，必须由用户在 Gate 4 决定。没有批准方案时不实现受保护 API 的生产调用。
- 本基线没有离线可用、跨次缓存或历史记录要求；建议首版仅以内存状态保存当前列表和当前详情，不引入数据库/持久化依赖。此为技术提案，待 Gate 4 批准。
- API 基础地址和环境配置不得硬编码凭据；生产/测试配置差异须通过不含秘密的配置注入。
