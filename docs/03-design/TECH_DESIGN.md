## 1. 设计边界

本设计只覆盖 Gate 3 已批准的 REQ-001 新游列表及 REQ-002 游戏详情。产品仅包含 `GAME_PUZZLE`、`GAME_CASUAL`，不限定国家/地区；不增加登录、搜索、筛选、收藏、分享、外部跳转、付费、同步、通知或其他功能。

本文为 Gate 4 技术方案及后续密钥方案、列表单页读取策略调整后的设计基线，不批准需求变更或具体开发任务。Gate 5 任务拆解及后续开发门禁仍须分别执行；日期 API 契约验证和本地凭据配置须在相应任务 Ready 前落实。

## 2. 架构与模块职责

建议使用单 App target、SwiftUI 展示层、可注入的应用服务和 API 客户端。App 直接通过 HTTPS 请求上游 API，并在 App 本地加密保存 API Key；不增加代理组件。模块按职责划分如下：

| 模块 | 职责 | 主要输入 / 输出 |
|---|---|---|
| `GameListFeature` | 列表与详情导航；呈现加载、内容、空结果、失败四种状态；不承载 API 细节 | ViewModel 的只读状态、用户点击事件 |
| `GameListViewModel` | 管理一次启动刷新、请求取消、状态转换及列表选择 | `GameCatalog`、日期时钟/日历 |
| `GameCatalog` | 仅请求 Casual 类别第一页，负责过滤、去重、排序，并按 ID 加载详情 | `GameAPIClient`、`ReleaseDateWindow` |
| `GameAPIClient` | 直接调用 playapi.info 的列表/详情接口，解码响应并映射传输错误；从本地凭据存储读取 API Key 并添加认证头 | API 配置、本地凭据存储 |
| `ReleaseDateWindow` | 以设备本地日历构造包含第 7 与第 15 日的时间范围 | 当前时刻、设备 `Calendar` / `TimeZone` |
| DTO / Domain Models | 将 API 响应与列表/详情展示数据分离；模型细节见 `DATA_MODEL.md` | 经过验证的字段 |

依赖方向为 View → ViewModel → Catalog → GameAPIClient → playapi.info。UI 不直接发请求；API 客户端负责认证头、本地凭据读取、传输和解码，不决定业务日期范围或 UI 状态。所有边界依赖应可替换，以便不联网测试日期、聚合与状态机。

**密钥处理是实施前置条件。** `/new` 是需认证接口。按用户后续决定，App 在本地加密保存 API Key，运行时读取并通过 HTTPS 认证头请求上游；不使用代理。密钥不得以明文写入源码、资源、构建配置、仓库、文档、测试证据或日志。本项目不上架 App Store，仅支持本地运行。加密保存保护的是静态存储状态，不能阻止拥有本地 App/设备访问权的人从运行态或二进制中提取密钥；本方案不提供面向分发客户端的共享密钥安全边界。

## 3. SwiftUI 页面与状态

### 列表页

- 单一列表页面，不提供搜索框、筛选器、排序控件或外部链接。
- 每行只使用 API 已验证且需求允许的列表字段。显示标题、图标、类别和首次上架日期；其中 `icon`、`category`、`released` 均见 API 字典。不得展示商店 URL 或把行/图片设为外部跳转。
- 点击行进入对应详情；页面状态只允许：
  - `loading`：首次加载中。
  - `loaded([GameSummary])`：有结果，展示按 `released` 从新到旧排列的列表。
  - `empty`：仅显示 `No games found`。
  - `failed`：仅显示 `Unable to load games`。
- 加载失败页不同时展示旧列表、错误详情、重试按钮或其他提示；空结果页也只展示规定文案。

### 详情页

- 由列表行选择进入；以应用 `id` 请求 `/api/v1/app`。
- 显示策略仅限 API 实测详情字段，具体候选字段与未批准字段说明见 `DATA_MODEL.md`。不显示或使用 `url`，不提供外部跳转。
- 详情失败时，详情内容区域仅显示 `Unable to load games`，不自动重试；保留系统导航返回列表。不增加错误详情、重试或外部跳转。

## 4. 网络、聚合与刷新生命周期

### 请求策略

- 列表首次加载仅调用一次 `GET /api/v1/new?category=GAME_CASUAL&page=1&per=100`；不请求 Puzzle、不传日期参数、不并发、不请求后续页。
- 最多接收 API 默认排序的前 100 条，再由客户端按本地日期窗口过滤；这表示只展示 Casual 首页面内的匹配项，不保证覆盖该日期窗口内的全部记录。
- 对返回项按 `id` 去重，再按 UTC `released` 时间从新到旧排序。相同时间的稳定次序以 `id` 升序作为确定性技术排序，不增加 UI 排序功能。
- 该唯一请求成功且响应有效后才能发布列表；请求、解码或响应契约失败时整次加载失败并只显示 `Unable to load games`。
- 网络请求应设置合理超时，具体时长待实现任务定义并测试；不得记录密钥、认证头、完整请求 URL（若含敏感参数）或未经脱敏的响应。

### 本地日历日窗口与 UTC `released`

业务规则按用户设备本地日历日计算，不按滚动的 24 小时差计算。令设备当前本地日历日为 `D`，设备当前 `Calendar` / `TimeZone` 下：

1. `start = startOfDay(D - 15 calendar days)`。
2. `endExclusive = startOfDay(D - 6 calendar days)`。
3. 候选记录须满足 `releasedUTC >= start` 且 `releasedUTC < endExclusive`。这精确包含本地日期 `D-15` 至 `D-7` 共 9 个日历日，含第 15 天和第 7 天的全部时刻。
4. 先解析 API UTC ISO 8601 时间戳为绝对时刻，再与上述本地日历边界对应的绝对时刻比较；不截断 UTC 日期后直接与本地日期比较。窗口跨越夏令时变化时，以日历日边界为准，而非固定秒数。
5. 列表 API 请求不传日期参数；客户端只对收到的 Casual 首页面结果执行上述精确日期过滤，因此不承诺覆盖所有符合日期窗口的 Casual 游戏。
- 当前时间、日历和时区必须从可注入的系统时钟/环境取得，测试可固定；刷新时快照一次 `now`，用于本次 Casual 结果过滤。

### 刷新生命周期

- 每次 App 进入完全启动流程时触发一次列表刷新。一次启动内不得由页面重复出现、视图重绘或从后台回前台额外触发刷新。
- App 从后台返回前台不自动刷新。首版不引入定时刷新、推送刷新、后台刷新或用户手动刷新入口。
- ViewModel 对同一启动刷新采用单飞策略：进行中的同次刷新不重复发起；若生命周期意外启动新一轮请求，应取消并隔离旧任务，旧任务不能覆盖新状态。
- 启动时显示 `loading`，请求全部成功后进入有内容或 `empty`；发生任一失败进入 `failed`。错误状态不自动重试。

## 5. 详情数据流

列表行的 `id` 作为详情请求唯一键。进入详情时 `GameCatalog` 调用 `GET /api/v1/app?id=<id>`，校验响应 `id` 与请求 ID 一致后映射为详情模型。详情不从列表字段推造 API 未返回的字段；列表中已有的信息可在详情展示前作为临时已知值，但不能据此替代详情 API 响应或声称字段已完整。详情 API 错误分类见第 7 节。

## 6. 并发与取消

- 列表加载只发起一个 Casual 首页面请求，不存在类别请求并发；Swift 6.0 编译器、Swift 6 语言模式及完整并发检查已获批准。
- 父任务取消时取消当前请求；离开详情页可取消未完成的详情读取。底层 URL 加载必须响应取消。
- 每次加载携带递增请求代号或任务身份；仅当前有效任务可提交状态。取消不是加载失败，不显示错误文案；被取消的旧任务不得清空或覆盖新任务结果。
- 合并、去重、过滤、排序为纯计算步骤，完成后一次性提交不可变结果，避免 UI 观察到半成品。

## 7. 错误映射

| 错误类别 | API / 客户端示例 | 列表可见结果 | 处理约束 |
|---|---|---|---|
| 传输失败 | 无网络、超时、连接中断 | `Unable to load games` | 不展示底层错误，不自动重试 |
| 认证 / 配置 | HTTP 401、缺少本地凭据 | `Unable to load games` | 不记录凭据或认证头 |
| 服务端 / HTTP | 非成功状态码、HTTP 5xx | `Unable to load games` | 保留脱敏诊断类别；不展示原始响应 |
| 解码 / 契约 | JSON 无法解码、必需字段缺失或类型错误 | `Unable to load games` | 整次类别聚合失败，不发布部分列表 |
| 首页面响应无效 | 返回页码、条数或分页元数据与第一页契约不符 | `Unable to load games` | 不请求后续页；第一页数据不满足契约时整体失败 |
| 详情未找到 | `/app` HTTP 404 `not_found` | `Unable to load games` | 不生成假详情，不打开商店链接 |
| 详情其他失败 | 传输、认证、服务端、解码失败 | `Unable to load games` | 内部分类与列表错误一致 |
| 用户取消 | 任务被新任务/页面生命周期取消 | 不显示失败文案 | 丢弃过期任务输出 |

日志仅允许记录不含密钥、认证头、敏感 URL、原始响应或可识别用户信息的技术错误分类。首版是否保留本地诊断日志待实现任务确定；不增加遥测/分析 SDK。

## 8. 安全、存储与配置

- 上游 API Key 由 App 使用 CryptoKit AES-GCM 加密后保存；随机生成的 256-bit 对称密钥与密文分别存入系统 Keychain，Keychain 项目使用 `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`。不以明文放入源码、资源、plist、构建设置、Git、日志或截图。
- 本机运行从 Git 忽略的仓库根目录 `playapi-key.local` 读取单行配置。先由 Xcode 将 App 安装到目标，再运行 `scripts/run-local.sh simulator <模拟器设备 ID>` 或 `scripts/run-local.sh device <真机设备 ID>`；脚本通过对应启动工具的临时进程环境传入，不写入共享 scheme、构建设置或命令行参数。App 启动时验证、加密并持久保存该值，然后清除进程环境中的变量。后续凭据访问仅经 `CredentialStoring` 接口；视图和 ViewModel 不接触 Key。
- 缺失配置表示尚无凭据；空值、多行值及 Keychain/解密失败均转换为脱敏错误，不暴露底层错误文本或凭据。调用方不得在凭据不可用时发出认证请求。
- AES-GCM 与 Keychain 保护本机静态存储状态，不阻止拥有本地 App/设备访问权的人从运行态或二进制中提取密钥；本方案适用于本地运行、不发布的交付边界，不构成面向分发客户端的共享密钥安全边界。
- 本基线没有离线可用、跨次缓存或历史记录要求；首版仅以内存状态保存当前列表和当前详情，不引入数据库/持久化依赖。
- App 配置固定的 HTTPS 上游 API 地址；上游 API Key 加密保存在 App 的本地受保护存储中。
