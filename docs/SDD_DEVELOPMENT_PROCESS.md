# SDD 开发流程规范

- 文档编号：SDD-001
- 版本：V1.0
- 状态：用户审核通过
- 适用项目：Google Play 新游观察站

## 1. 基本原则
采用阶段门禁式 SDD。先规格、后实现；每阶段用户审核通过后才可进入下一阶段；API 能力以实测证据为准；一个任务一个独立功能；每项任务完成后单独审核；规格变更先申请、后审批。

## 2. 角色职责
- 用户：产品负责人、需求确认人、技术决策人、阶段审核人。
- ChatGPT：需求分析、规格编写、技术方案分析、任务拆解、变更评估。
- Codex：按批准规格执行代码修改、测试和任务交付。
- AI 不拥有最终需求决策权或规格批准权。

## 3. 技术基线
- Xcode 16.1。
- 最低部署目标 iOS 16.0；Swift 6.0 编译器与 Swift 6 语言模式。
- UI 优先 SwiftUI。
- SwiftUI 无法满足已批准需求时，可评估 UIKit。
- 其他 UI 框架必须先提交方案并获用户批准。
- 网络使用系统 `URLSession`、`Codable` 和 Swift structured concurrency；不添加第三方依赖，不使用持久化层。
- App 直接通过 HTTPS 调用固定的上游 API；API Key 在 App 内本地加密保存，视图和 ViewModel 不接触密钥。不使用本机代理、后端代理或生产托管。
- 项目仅交付本地可运行版本，不在 App Store 上架。App 内加密只保护静态存储，不保证密钥无法从运行态或客户端二进制提取。

## 4. 文档与状态
所有正式文档存放于项目 Git 仓库。需求、API 能力、任务需使用唯一 ID，并记录状态、来源、证据、验收标准和关联项。
建议状态：待分析、待验证、已验证、已确认、开发中、待审核、已通过、不支持、已废弃。

编号前缀：
- REQ：产品需求
- API：API 能力/接口
- TECH：技术设计
- TASK：开发任务
- TC：测试用例
- CR：变更申请
- ADR：技术决策

## 5. 阶段与门禁
### 阶段 0：项目初始化
建立 Git 文档体系、PROJECT.md、流程规范和模板。Gate 0：用户审核通过。

### 阶段 1：需求分析与规格定义
整理需求、业务规则、优先级、验收标准和待确认问题。未经验证的 API 能力不得写成确定功能。Gate 1：用户审核通过。

### 阶段 2：API 能力验证
只进行 API 请求、参数、字段、分页、筛选、额度、频率、异常和更新情况验证。不写正式业务代码、不开发正式 iOS 页面。独立验证脚本不得作为正式业务代码。凭据必须脱敏。Gate 2：用户审核 API 报告通过。

### 阶段 3：需求修订与基线冻结
根据实测结果保留、调整、移出或继续标记待验证的需求。任何调整须用户确认。Gate 3：用户批准正式需求基线。

### 阶段 4：技术方案设计
设计架构、模块、UI、网络、数据模型、错误处理、密钥管理和依赖。SwiftUI 优先，UIKit 作为必要备选；其他 UI 框架须审批。Gate 4：用户批准技术方案。

### 阶段 5：开发任务拆解
一个任务只实现一个独立功能。任务必须有已批准需求、明确范围、依赖、验收标准和测试用例。Gate 5：用户审核任务清单。

### 阶段 6：规格驱动编码
一次只执行一个任务。开始前阅读项目和关联规格，提交实施计划并获确认；完成后提交修改清单、测试结果、偏差和未解决问题。当前任务未审核通过，不得开始下一个任务。Gate 6：逐任务审核。
Gate 5 批准任务清单不等于批准启动任务；每项任务开始前均须单独提交实施计划并获用户确认。当前没有任务获准启动，包括 TASK-001。

### 阶段 7：整体测试与交付
执行单元、集成、业务流程、UI、异常、安全和追踪完整性检查，交付本地可运行版本。Gate 7：用户最终验收。

## 6. 规格变更
流程：提交 CR → 影响分析 → 用户审批 → 修改规格 → 更新任务和测试 → 继续工作。
AI 不得批准自己提出的变更。未批准的建议不得写入正式规格基线。

变更申请至少记录：编号、标题、原因、当前规格、建议内容、影响需求/设计/任务/测试、风险、工作量、进度影响、申请人、审批结果和审批人。

## 7. 追踪关系
正式功能需建立需求 → 技术设计 → 开发任务 → 测试用例的追踪关系。没有已批准需求的任务不得开始；没有验收标准和测试依据的功能不得标记完成。

## 8. AI 执行约束
开始前确认规格已批准、任务可执行、依赖满足、验收标准明确。执行中不得超范围修改、擅自加依赖或更改 UI/架构/业务规则。发现规格冲突或 API 不符时暂停受影响工作并报告。

## 9. Ready / Done
Ready：需求和技术设计已批准、任务范围和依赖明确、验收标准与测试用例已定义、用户批准开始。
Done：实现符合范围、测试通过、修改清单已检查、敏感信息安全、文档和任务状态更新、完成报告提交、无未说明偏差。Done 后仍须用户审核。

## 10. 文档与版本
正式规格记录文档编号、名称、版本、状态、创建/更新时间、编写人、审核人、审核时间和变更记录。Git 提交不能替代用户审批。用户批准的规格应有清晰 Git 记录或标签。
